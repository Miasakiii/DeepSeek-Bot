## 为什么

2026 年 6-10 月，Anthropic Claude Tag、xAI Grok Bot、Meta Muse、Manus Cue、OpenAI Dots、Instinct 密集发布，把"Personal Agent"从开发者玩具做成 C 端产品。这篇文章是产品视角的复盘：为什么这批产品选在这个时间点、与早期 ChatBot 和 OpenClaw/Hermes 这类开源 Agent 差在哪、未来七条技术趋势。

DS Bot 与文中产品处在同一赛道：长期身份、多 Bot 团队、群聊、派活、记忆、独立浏览器、审批与沙箱。文章里对 Grok Bot 的描述——"用户可管理多个长期存在的 Bot、支持多角色设定、Bot 间交互"——几乎就是 DS Bot 现在的形态。所以这份清单不是"学习新方向"，而是回答两个问题：

1. 七条趋势里，DS Bot 哪些已经做到、哪些是缺口？
2. 缺口里，哪些值得补、以什么顺序补，怎么和现有路线（解耦 `A → B1 → C0 → C → B2 → D`、主动性 `P0–P4`）叠加？

本文的定位是一份**决策清单**：每个借鉴项给出文章依据、DS Bot 现状（带出处）、落地位置、优先级与验收口径，供维护者逐条拍板。**趋势①（主动预判）的主设计已经存在**——[主动性基座](2026-10-26-proactivity.md)（下称"proactivity 提案"，状态：待拍板）——本文不重复它，只标注它与本文其余条目的依赖关系。

### 事实基线（代码 vs 设计承诺的校准）

规划前先把"已实现"与"设计里写了"分开。下面几条来自运行时盘点（`ds-bot/src/host/` 45 个模块、`app/` 17 个文件），与文档承诺不一致时以这几条为准：

1. **去 DSH 化尚未发生**：自有 LLM 层（`llm.js`）、自有 HTTP 出口（`outlet.js`）、自有窗口 UI（`app/ui`）已落地；turn 循环、工具执行、会话仍由 DSH 跑（`llm.js:3-5`、`outlet.js:1-8`）。C 之前的能力规划都不能假设自有循环。
2. **浏览器自动化默认关闭**：Playwright 三后端必须配 `browserPlugin` 才挂（`browser-plugins.js:107-112`）；`read_browser` 只在桌面窗口开着时可用（`browser.js:246-253`、`browser.js:34-46`）。
3. **定时任务依赖 DSH schedule**：服务缺失时功能报 unavailable（`schedules.js:93-101`），不是 DS Bot 自带调度器。
4. **"Bot 有记忆"= 每轮结束一次模型 review**（`memory.js:1703-1729`），不是持续学习；`memoryReview:false` 可关。
5. **私聊普通轮次没有停止 API**：只有 Main 的 `stop_bot`、群的 `stop-member-work`、浏览器面板的 `browser-stop` 三条路径会 cancel（`tools.js:267-292`、`groups.js:888-901`、`channel.js:494-508`）。
6. **没有外部入口、移动端、云执行、自有后台任务、多租户**；插件只有 `POST /api/bot` 与 `GET /api/bot/feed` 两个路由（`channel.js:531-541`、`feed.js:104-127`），`/api/bot` 的 83 个 case 是给自己 UI 的 RPC，没有第三方 API token/scope/限流。
7. **三种形态的安全模型不同**：Docker 只有 `danger-full-access`（容器即边界，`docker/docker.patch.yml:1-12`）；桌面走 DSH 权限预设；自有 outlet 只绑 loopback（`outlet.js:167`）。
8. **三处 DSH 版本不一致**：app 锁 `0.2.1-rc.2`（`app/package.json:23`）、Docker 默认 `0.2.0-rc.2`（`Dockerfile:10`）——跨形态规划要以各自 profile 为准。
9. **代码里没有 TODO/FIXME 债务标记**（全量 grep 为 0），空白只能从结构判断，不能靠注释兜底。

## 一、文章结论摘录（只摘对 DS Bot 有决策含义的）

**发布历程**：6 月 Claude Tag（Slack 里的"数字同事"）→ 8 月 Grok Bot（点燃赛道）→ 9 月初 Meta Muse（C 端引爆）→ 9 月底 Manus Cue 与 OpenAI Dots（两天内）→ Instinct（嵌入短信/电话/邮件、零安装）。

**与早期 ChatBot 的区别**：定位没变（都是帮人完成任务），能力从"问答 + 简单工具"升到"与 Cowork/Coding Agent 同一水平线"，对早期 Chat APP 是降维打击。

**与 OpenClaw/Hermes 的区别**：技术差距已不大（持续运行、自主规划、记忆、工具调度、多 Agent、定时任务都有），差别在**用户心智与成本**——开源 Agent 部署门槛高，只火在开发者圈；这批 Personal Agent 靠"下载一个 APP 或直接在 IM 里说话"出圈。

**文章给出的定义与八要素**：围绕"个人"的任务目标、上下文与授权，一段时间内自主决策执行、保留记忆与状态、把结果反馈给个人。八要素：服务对象、身份、上下文、执行、运行时间、边界、自闭环、持续学习/自进化。

**六大能力提升**：①入口更低门槛；②上下文更全（通讯录、邮箱、IM、聊天记录）；③操作权限更大（直接操作电脑/手机/APP，不只是浏览器）；④**自己的云电脑**（7×24 在线、不抢设备、端云协同）；⑤模型能力提升带动 Computer/Browser/Mobile Use；⑥长程记忆与持续自进化。

**七条未来趋势**（本文的对照轴）：①被动响应 → 环境感知 + 主动预判；②数据拼接 → 动态个人知识图谱 + 心智模型；③API 调用 → 通用 GUI 操作 + 端到端规划；④云端独立 → 端云一体 + 隐私可信执行；⑤能力叠加 → 世界模型 + 具身认知；⑥记忆积累 → RSI + 个性化价值对齐；⑦单 Agent → 多 Agent 生态 + 人机协同。

**文章的一句总结**：这一轮是"量变到质变"，厂商换新名字是为了让消费者认知"这是一个全新的东西"。

## 三、借鉴清单

### 3.1 产品层

**P-01 低门槛入口：邮件 / IM / Webhook 网关**
- 文章依据：入口更低门槛是 Personal Agent 出圈的第一原因；Instinct 不装 APP，直接嵌在短信、电话、邮件里。
- 现状：入口只有桌面 app、DSH 插件、Docker Web（README.zh.md:20-52）；移动端是 thin client 且未实现（decouple.md:126-134、ROADMAP.md:77）；代码里只有 `POST /api/bot` 与 `GET /api/bot/feed` 两个路由，83 个 case 都是给自有 UI 的 RPC（`channel.js:145-518`、`channel.js:531-541`），没有第三方 API token/scope/限流；`connectors.js` 只认 `github`（`connectors.js:119-121`）；Docker 形态下手机只能用 DSH Web 前端访问，不是 DS Bot 自己的入口。
- 借鉴：host 增加 inbound gateway，把"邮件 / Telegram Bot / 通用 webhook"的消息映射为某个 Bot 的会话消息，回复走同一通道；通道与用户身份绑定，审批回到桌面 app（或通道内一次性确认码）。需要同时补一层"外部凭证 → 用户"的绑定与限流（现在完全没有）。
- 落地位置：`ds-bot/src/host/` 新模块（如 `gateway.js`），复用 `channel.js` 的消息注入路径；不新增 DSH 依赖。
- 优先级：**P2**（价值高，但依赖常驻在线 T-08 与会话注入稳定；且先做 C 之后的移动端更顺）。
- 依赖：T-08、T-09；`api/bot` 协议不变（decouple.md:176）。
- 验收：邮件发一句"帮我看下 X"，Bot 在自己会话里跑完，邮件回结果；断线重连不丢消息；审批仍在桌面完成。
- 不做：不做微信个人号/短信/电话（合规与成本），不做双端同时在线抢占。

**P-02 主动性基座（采纳 proactivity P0–P4）**
- 文章依据：趋势①；主动性 = 身份 × 数据源 × 记忆；主动的本质是"目标 − 现状 = 差距"；真正卡人的是责任归属。
- 现状：proactivity 提案已完整设计目标、提案、认领、live、唤醒、审计、分层与退路（proactivity.md:46-230），状态"待拍板"、代码零（`GOAL_TOOLS` 被显式屏蔽，tools.js:17-20）。
- 借鉴：**本条不新增设计，建议直接进入拍板**。P0（目标 + live）与 P1（提案 + 认领）不依赖定时器，可按提案原文落地；P2（主动回合）的 tick 边界是待拍板第 7 条。
- 优先级：**P0**（最高杠杆；C2 的欠账，dsh-concessions.md:17）。
- 依赖：无（P0/P1 全部在 `ds-bot/` 内，不动 `app/`）。
- 验收：按 proactivity.md:222-223 的 P0/P1 验收项。
- 不做：L5 自动执行、推断用户没说出口的目标（proactivity.md:247）。

**P-03 环境事件源与用户情境**
- 文章依据：趋势①"不再依赖语音唤醒或文本匹配，而是情境计算 + 意图预测"。
- 现状：proactivity 只把"工作文件夹变化 / GitHub 连接器事件 / RSS"列为 P4 可选（proactivity.md:109、226）；没有"用户情境"（在不在电脑前、忙不忙、免打扰之外的状态）。
- 借鉴：在 proactivity 的 L3 事件源上补三档——(a) 本地文件 watcher（工作文件夹/下载目录变化）；(b) 连接器事件（GitHub issue/PR、后续邮件/日历只读）；(c) 轻量用户情境（最近活动时间、当前窗口标题分类，本地处理不上传）。情境只用于"是否值得唤醒/是否打扰"的判断，不推断目标。
- 落地位置：`wakes.js` 的 event source 抽象 + 各 source 适配器；情境进 `state.live` 的 `waitingOn/doing` 推断，不新增提示词。
- 优先级：**P1**（等 P0/P1 拍板后作为 P2 的事件源扩展）。
- 依赖：P-02；macOS/Windows 原生 API 需分平台实现（仓库已有 Electron 壳与 Win32 窗口处理，`app/src/main.mjs`、`app/src/window-frame.mjs` 可参考）。
- 验收：改一个工作文件夹里的文件后，目标相关 Bot 在下一次 tick 被唤醒一次（且只一次）；免打扰时段不唤醒；无目标时事件只记录不唤醒。
- 不做：不读屏幕内容、不做键盘记录、不上传任何情境数据。

**P-04 常驻在线：托盘 / 开机自启 / 通知**
- 文章依据：六大能力提升④"自己的云电脑，7×24 在线不中断"；趋势①主动预判需要一直在场。
- 现状：桌面 app 关窗即退（macOS 明确，desktop-app.md:110）；代码确认**没有系统级推送/通知**，窗口不在线时事件只存日志；没有开机自启、托盘、后台常驻。关窗后 Electron 进程与 Host 子进程的关系，直接决定 Bot 浏览器与自有 UI 是否还可用（`main.mjs:392-465`、`browser.js:34-46`）。Docker 可常开但面向 NAS 用户（README.zh.md:50-52）；proactivity 也承认"桌面关了就不工作"（proactivity.md:264）。
- 借鉴：桌面 app 增加"后台常驻"模式：关窗只隐藏窗口（Host 与浏览器桥继续跑）、最小化到托盘、开机自启（可选）、有唤醒/审批/失败时系统通知；退出前停引擎的语义保留（单写者锁要正确释放）。这是"7×24"的最低成本路径，不动数据模型。
- 落地位置：`app/src/main.mjs`（托盘、单实例、自动启动）、`app/ui`（设置页开关）；Host 不感知。
- 优先级：**P0**（独立于主动性，可先做；对"主动"体验是前置）。
- 依赖：无；与 B1 的自有 UI 兼容。
- 验收：关窗后进程在托盘；重启机器后自动启动（若开启）；有主动回合/审批时出现系统通知；退出时 `state.lock` 释放，另一个 dsh 能接管。
- 不做：不做 Windows 服务（与用户桌面会话、Electron 渲染解耦成本高），不做 macOS LaunchAgent 的 LaunchDaemon。

**P-05 协作深化：Bot 间旁路问答（`ask_bot`）与人机工作流**
- 文章依据：趋势⑦"专业化 Agent 组成的协作网络：自主沟通、分工、校验"；人机协同工作流。
- 现状：派活树、状态、请求身份已很强（bot-handoffs.md:20-116）；**Bot 对 Bot 的 `ask_bot` 明确未做**（btw.md:59"另行提案，需维护者确认"）；"任务对象、进度查询、只提问不动手留给独立 app"是既有边界（bot-handoffs.md:114）；群聊坚持一次一人、不并行（group-chat.md:10、24、69-70）。
- 借鉴：v1 只做 `ask_bot`——在派活树之外允许"问一句不派活"的旁路问答（不产生 work、不改验收关系、不进派活树），用于"这件事你知道结论吗""文档里那句话在哪"这类低代价查询；v2 再评估"人机工作流"（群里的步骤化流程），但不引入看板与任务对象。
- 落地位置：`tools.js` 新工具 + `delivery.js` 新消息类型 + `bot-handoffs.md` 补一节。
- 优先级：**P1**（设计成本低、和现有派活不冲突；需要维护者确认边界）。
- 依赖：无（DSH 上也能跑）；需先裁决"只提问不动手留给独立 app"这条边界。
- 验收：A 问 B 一句、B 直接答、A 的派活树不产生子活、A 不回交；B 正在干活时问题排队不打断；群里不出现 `ask_bot` 造成的发言。
- 不做：不做并行群聊、不做 Bot 自发约定。

**P-06 Bot 模板与共享成员**
- 文章依据：趋势⑦"角色定义框架、信任机制"；Claude Tag 的"共享成员"。
- 现状：Bot 可自定义名字/角色/指令/模型/character（README.zh.md:64-70），但没有导出/导入模板；能力包（MCP+技能组合）框架已在但具体包未定（bot-runtime.md:55-60、73）。
- 借鉴：Bot 配置（角色标签、指令、模型、character、能力引用）可导出为模板文件，供团队内复用或分享；导入时校验权限、不覆盖已有 Bot、能力缺失显式列出。
- 落地位置：`roster.js`（导出/导入）+ `src/client/create-bot.js`（界面）；模板文件进 `memory/` 之外的新目录（如 `templates/`）。
- 优先级：**P2**（生态价值，但单机用户短期内需求弱）。
- 依赖：插件生态三档（decouple.md:144）落地后更顺。
- 验收：导出一个 Bot → 在另一台机器导入 → 名称冲突可改、能力缺失有提示、不导入密钥。
- 不做：不做在线市场/商城。

**P-07 开放协议与本地 Agent CLI**
- 文章依据：趋势⑦"标准化 Agent 通信协议"；趋势⑥"能力上限由生态决定"。
- 现状：MCP 已用于工具（Capabilities）；DSH 引擎/界面插件生态在 B1 后终止（decouple.md:189）；本地 Agent CLI 接入是愿景第 10 条、ROADMAP 列为并行轨道但"无设计文档"（vision.zh.md:31、ROADMAP.md:91）。
- 借鉴：先做 MCP 侧的"外部 Agent 才能"（把别的 Agent CLI 当工具/能力挂进团队），再做 A2A 式的跨团队 Bot 消息（需要一个公开协议标准成熟）。
- 落地位置：`capabilities.js` 的 MCP 客户端（C 后换中立 SDK 薄桥）。
- 优先级：**P2**（fleet CLI 部分 P1 设计、P2 实现）。
- 依赖：C（自有工具面）或现有 DSH MCP 客户端；协议外部标准。
- 验收：把一个本地 CLI Agent 挂成 Bot/能力，能完成任务并在群里说话；不新增 DSH 补丁。
- 不做：不自己发明对外协议；不把 DSH 插件生态原样搬过来。

**P-08 信任体验：可解释与可审计**
- 文章依据：趋势①"它为什么说话"、趋势⑥"个性化价值对齐"；文章强调责任归属（谁定义问题、失败代价、能否验证）。
- 现状：审批、密钥、二次确认、删除核对都已完整（roles-and-permissions.md:10-36、browser-plugins.md:21-25）；但"Bot 为什么做这个决定"分散在各处，没有统一的解释面；主动回合审计还只是提案（proactivity.md:141）。
- 借鉴：统一"解释卡"——每次有外部影响或不可逆动作时，展示：目标（若有）、证据锚点、授权范围、可撤回性；主动回合在界面上可点开"它为什么说话"（proactivity 已设计）。
- 落地位置：`channel.js` state 视图 + `src/client` 面板；与 proactivity 的审计共用。
- 优先级：**P1**（和 P-02 一起做，成本低）。
- 依赖：P-02（目标/提案对象存在后才有"解释什么"）。
- 验收：任一主动回合都能在界面看到 goal、事件、差距、授权范围；对外动作的必填三字段缺失被拒（proactivity.md:151-159）。
- 不做：不做通用可解释性研究，只做"动作前的授权摘要 + 动作后的证据锚点"。

### 3.2 技术层

**T-01 用户画像与心智模型（user model）**
- 文章依据：趋势②"从读过你的数据升维到真正认识你：你和谁聊过什么、你为什么这么聊、你在意什么、决策习惯"。
- 现状：只有记忆条目（事实/偏好/纠正，README.zh.md:68）；无画像对象；记忆冻结导致回合中途看不到新条目（context-and-memory.md:138）；无"为什么"层。
- 借鉴：新增**非记忆的画像对象**（不塞进记忆段、不参与冻结）：偏好、底线、决策风格、活跃时段、常用工具/入口、典型任务；由记忆整理任务增量维护，固定上限（≤2 KB），可按需注入或 `read_profile` 读取。画像与记忆分开存，避免污染记忆的冻结与 `recall` 语义。
- 落地位置：`memory.js` 旁新增 `profile.js`、`state.profile` 索引、`memory/profile.md` 正文；面板可看可改。
- 优先级：**P1**（与 P-02 的 live 同期做，两者都是"上下文摘要"性质）。
- 依赖：无。
- 验收：连续聊一周后画像里出现稳定偏好与决策风格；Bot 在 system prompt 或 `recall` 中能用上；用户能删改；画像不写进记忆段（提示词前缀仍稳定）。
- 不做：不推断敏感属性（健康、政治、宗教、性取向等）；不做人格评分。

**T-02 记忆检索升级：语义检索 + 时间有效性 + 冲突检测**
- 文章依据：趋势②"结构化知识图谱""因果推理"；趋势⑥"持续学习"。
- 现状：FTS5 全文 + 主题整份读（context-and-memory.md:73-76、95）；记忆条目只有 `added` 元数据；多个 Bot 可能写入矛盾事实，无冲突检测；`open|confirmed` 只是提案（proactivity.md:196-202）。
- 借鉴：(a) 混合检索：FTS5 + 本地小嵌入模型（或远程嵌入路由）做语义召回，结果合并排序；不改变记忆文件格式。(b) 条目增加 `validFrom` / `supersededBy`（可选字段，旧条目回填为空）。(c) 写入时检测同名主题下的矛盾（同主语不同结论），标 `open` 并提示。
- 落地位置：`chat-index.js` 扩展或新增 `memory-index.js`；`memory.js` 的写入校验。
- 优先级：**P1**（T-01 之后；语义检索需选型，嵌入模型成本要评估）。
- 依赖：模型路由（阶段 A 已有自有 LLM 层，可复用）。
- 验收：语义问"上次说的那个部署脚本放哪"能召回含"部署"但不含"脚本"的条目；改一条记忆后旧结论不被当现行；每个 Session 的提示词前缀仍可命中缓存。
- 不做：不改记忆的 Markdown 格式与大小上限；不做向量数据库依赖（SQLite 扩展或轻量库）。

**T-03 知识图谱（观察项）**
- 文章依据：趋势②"把交互、行为、偏好构建成实时更新的结构化知识图谱"。
- 现状：无。
- 判断：与 DS Bot 的记忆格式（一行一条 + 4000/16000 字符上限 + 40 主题）张力大（context-and-memory.md:93-95）；真正的图谱需要改存储与查询，收益主要在大规模个人数据（几百上千实体）场景，单机单用户短期看不到回报。
- 结论：**观察，不立项**。等 T-01/T-02 跑出真实数据量后再评估"实体索引层"（不动记忆本体，只建旁路索引）。

**T-04 桌面 GUI 操作（非浏览器）**
- 文章依据：趋势③"像人一样看屏幕、点按钮、输文字，能操作任何有界面的应用"；六大能力提升③"直接操作电脑、手机和各种 APP（不只是浏览器）"。
- 现状：只有两种浏览器机制——用户驾驶的 Electron `<webview>`（Bot 只能 `read_browser`，窗口不在就不可用，`browser.js:246-253`、`browser.js:34-46`）与可选的 Playwright 三后端（默认不挂，`browser-plugins.js:107-112`）；无桌面窗口/原生控件操作；**没有自有沙箱**，完全依赖 DSH permission preset（`permissions.js:11-34`、`folders.js:142-146`）；Docker 形态没有窗口侧。
- 借鉴：分两档——(a) 只读档：屏幕截图 + 窗口列表 + 活动窗口标题，供 Bot 理解当前环境（多模态读图已有基础，CHANGELOG.md:309）；(b) 操作档：Windows UI Automation / macOS Accessibility 的原子动作（点击、输入、快捷键），**默认关闭、逐次审批、每步截图留痕**。继承浏览器插件的审批模型：读放行、写动作审批、付款/删除/登录交人（browser-plugins.md:21-25）。
- 落地位置：`ds-bot/src/host/` 新模块（如 `desktop.js`）+ `app/` 主进程提供原生桥（类似 browser-bridge 的租约）；Linux 先不做。
- 优先级：**P1 设计 / P2 实现**（C 阶段工具面自有化时一起做更省）。
- 依赖：C 的工具面（restrict/guard/审批/截图留痕）；Windows/macOS 双平台工作量翻倍。
- 验收：让 Bot 打开记事本写一行字并保存（mock 下可测）；每步截图与审批记录可回看；只读档在用户不允许操作时仍可用。
- 不做：不做跨平台通用"看屏幕"模型训练；不做无人值守的 GUI 操作（必须有人在场/审批）；Linux 与移动端暂不做。

**T-05 浏览器视觉操作强化**
- 文章依据：趋势③"操作前先在内部模拟一遍，大幅减少试错"。
- 现状：refs 后端已有 12 个工具（含 `browser_screenshot`、按编号点击/输入，`browser/refs.js:15-149`）；script 后端一次提交整段 JS；task 后端一个目标内跑最多 8 步（`browser/task.js:13-56`）；截图已作为图片块交给模型。缺的是**坐标级操作**（refs 失效时的兜底）；"操作前预览"归入 T-06 的统一预演层。
- 借鉴：补视觉定位——截图 + 坐标点击/输入（refs 失效时兜底），动作仍按四类写动作走审批。
- 落地位置：`browser/` 模块 + `tools.js` 新动作。
- 优先级：**P1**。
- 依赖：无（现有浏览器后端即可）。
- 验收：无 refs 的页面上用坐标完成一次填写；动作仍需审批；取消后页面不变。
- 不做：不做无审批的自动提交；不做验证码破解。

**T-06 操作前预演与轨迹审计（沙箱 dry-run）**
- 文章依据：趋势③"操作前先在内部模拟一遍"；趋势⑤"内置世界模型，理解软件交互逻辑"。
- 现状：文件/Shell 有审批与沙箱预设（roles-and-permissions.md:33-36），但没有"先看再执行"的统一预演；工具结果有 spill/截断（C12），但没有操作轨迹回放。**关键约束**：C 之前工具执行在 DSH 手里，DS Bot 无法拦截或包装 `write`/`shell` 的调用，能做的只有"提示词规则 + 审批摘要 + 事后轨迹记录"；强制预演要等 C 的工具面。
- 借鉴：分两档——(a) 现在：给 Bot 的规则加"写文件前先读、改前说明改什么"；host 监听工具事件生成操作轨迹（谁、何时、改了什么），可导出，密钥沿用现有替换；(b) C 之后：在自有工具面里做真正的 dry-run（写文件先 diff、Shell 可行时 dry-run、浏览器/GUI 先截图、MCP 写操作先列影响范围）。
- 落地位置：`turns.js`/`tools.js` 的事件监听 + 新 JSONL；C 阶段并入自有工具面。
- 优先级：**P0**（轨迹 + 规则，成本低）/ **P2**（强制预演）。
- 依赖：无（P0 部分）；C（P2 部分）。
- 验收：一次会话结束后能导出操作轨迹（时间、工具、参数摘要、结果）；轨迹里不含密钥；C 之后：改文件前显示 diff（可配置关闭）。
- 不做：不做完整快照/回滚（成本高，先记录）。

**T-07 任务链与目标验收（与 proactivity 的关系裁决）**
- 文章依据：趋势③"把模糊目标自动拆解为可执行子任务链，执行中实时重规划"。
- 现状：回合内自主规划是 DSH 的能力；跨回合只有派活树（bot-handoffs.md:74-89），没有目标/步骤对象；proactivity 已设计 goal + `acceptance[]`（可判定条件 + 证据锚点），但**没有 plan/step 对象**，且明确"不做看板式任务对象"（proactivity.md:250）。
- 判断：**不新增 plan 对象**。步骤化由 Bot 在回合内自主完成，跨回合的"做到哪"由 goal 的 acceptance + live 承担；如果未来发现需要步骤级跟踪，先补 acceptance（更细），不引入看板。
- 结论：**已覆盖（设计层面）**，不另立条目；只把"验收规则"推广到派活结果（派活交回时带 evidence）。

**T-08 常驻服务与"用户自己的端云"（BYO node）**
- 文章依据：趋势④"端云一体 + 隐私可信执行"；六大能力提升④"自己的云电脑"。
- 现状：纯本机；Docker 形态已在 `dsh web` 上部署（NAS/服务器可用，`docker/Dockerfile:1-52`），但那是 DSH Web 前端 + 插件，不是 DS Bot 自己的入口；单写者锁限制同一团队只有一个写进程（`home-lock.js`、CHANGELOG.md:317）；自有 outlet 只绑 loopback（`outlet.js:167`），手机不可达。
- 借鉴（**关键判断**）：不做厂商云、不做云分身（proactivity.md:252、vision.zh.md:36）；但可以做"用户自己的远端节点"——同一份 Docker 镜像部署在用户自己的 VPS/NAS，桌面 app 与远端通过同一单写者协议协同。**v1 不必等 C**：Docker + DSH Web 已能在用户自己的服务器上跑，先补"远端只读 + 消息排队 + 通知回桌面"即可；v2 再谈写主从：
  - v1（只读镜像）：远端节点以只读方式运行（看状态、收通知、queued 消息入队），写操作回桌面；
  - v2（写主从）：用户明确选择"以远端为主写者"，桌面变只读客户端——与现有 `home-lock.js` 语义一致，只是把"哪台机器持有团队"显式化。
- 落地位置：`home-lock.js` 扩展为"多节点锁"；`outlet.js` 的 token 认证 + TLS/SSH 隧道；Docker 镜像配置化。
- 优先级：**P1 设计**（v1 只读镜像 / 消息排队可以早做）/ **P2 实现**（v2 写主从，与 B2 合并）。
- 依赖：T-09 同步、DSH 解耦（C 之后远端节点才能不带 DSH）；安全模型（T-10）。
- 验收：桌面关着时远端节点能收消息、执行主动回合、写 live；桌面打开后能读到；同一时刻只有一个写者。
- 不做：不做厂商托管云；不做多用户共享团队；不做无 TLS 的跨公网访问。

**T-09 数据同步与多节点一致性**
- 文章依据：趋势④"简单事在手机秒回，复杂任务自动卸载到云端，结果实时同步"。
- 现状：`state.json` 整份重写 + 单写者锁（long-messages.md:20-23、CHANGELOG.md:317）；`state.json` 每次保存全量序列化（`store.js:297-334`），大团队会线性变慢——这是同步协议要一并解决的点。换数据位置是复制式迁移（desktop-app.md:68-73）；没有增量同步。
- 借鉴：v1 只做"只读节点跟随"（磁盘同步/`state.json` 热重载 + feed 事件）；v2 做增量同步（state 分片、journal 增量、冲突用单写者 + 版本号裁决）。**不引入数据库**，先做文件级。
- 落地位置：`store.js` 的写前日志与 `feed.js`；同步协议另写设计。
- 优先级：**P2**（依赖 T-08）。
- 依赖：T-08。
- 验收：两个节点数据差不超过 5 秒；写者切换后不丢消息、不重复执行。
- 不做：不做实时协作编辑；不做多写者（保持单写者原则）。

**T-10 密钥与隐私加固**
- 文章依据：趋势④"敏感数据本地加密，云端只收脱敏指令"。
- 现状：插件侧 `secrets.json` 明文（browser-and-secrets.md:42、CHANGELOG.md:325）；阶段 A 的自有 provider 密钥库已是 AES-256-GCM（decouple.md:44-47）；防泄漏是列举式替换（decouple.md:194）；日志有脱敏但 MCP 日志可能泄（dsh-concessions.md:21）。
- 借鉴：把阶段 A 的加密方案推广到 `secrets.json`（同一密钥管理）；日志脱敏补 MCP 响应体；远端访问强制 TLS 或 SSH 隧道。
- 落地位置：`secrets.js`；`home/keys.json` 复用。
- 优先级：**P1**（合规与信任，成本可控）。
- 依赖：无（不依赖 C）。
- 验收：`secrets.json` 落盘加密、旧明文文件一次迁移；日志 grep 不到密钥；现有测试全绿。
- 不做：不做 TEE/远程证明（单机不需要）；不做密钥托管。

**T-11 价值观与边界对象（价值对齐 v1）**
- 文章依据：趋势⑥"个性化价值对齐：你讨厌被打扰，它就永远不在非紧急时主动弹窗"。
- 现状：对齐规范散在权限、审批、免打扰、群规则里；没有显式的"用户价值观/边界"对象；proactivity 的免打扰是偏好、grant 是授权，但"你重视效率还是精确"这类排序没地方放。
- 借鉴：新增 `values.md`（或 `state.values`）：可编辑的短列表（≤10 条），如"不主动打扰""对外发送必须我确认""预算敏感""优先可逆方案"；注入提示词（小、稳定）并在动作前校验（不可逆动作与价值观冲突时升级为提案/审批）。
- 落地位置：`prompt.js` 注入段 + `approvals.js` 校验；面板可编辑。
- 优先级：**P1**（与 P-02/T-01 同期）。
- 依赖：无。
- 验收：写入"非紧急不主动"后，主动回合只在有明确目标进展时唤醒；违反价值观的动作被拦下并解释。
- 不做：不做自动学习价值观（只从用户明说的记忆里建议、用户确认才落）。

**T-12 失败复盘与技能沉淀**
- 文章依据：趋势⑥"每次任务成败中递归自我改进"；愿景"自我改进（待做）"（vision.zh.md:23）。
- 现状：记忆整理会保留/更新/删除条目（context-and-memory.md:112），但没有"失败"这个类别；技能只有用户手动加的能力（bot-runtime.md:55-60）；没有把重复流程固化成 skill 的机制。
- 借鉴：(a) 失败复盘：回合被用户打断、工具报错、目标未达成时，写一条 `lesson` 记忆（`open` 状态，用户可确认/删除）；(b) 技能沉淀：检测同一流程重复 3 次以上，生成 skill 草稿，用户确认后进能力库（复用 Capabilities）。
- 落地位置：`memory.js`（lesson 类型）+ `capabilities.js`（草稿/确认流程）。
- 优先级：**P1**（失败复盘）/ **P2**（技能沉淀，等 T-13 有度量）。
- 依赖：T-13（评估）；proactivity 的 `open|confirmed` 状态。
- 验收：一次失败后能看到 lesson 记忆；确认后不再重复同类错误；技能草稿不自动启用。
- 不做：不做提示词自动改写、不做权重训练（RSI 不做）。

**T-13 评估与度量（观察与自检）**
- 文章依据：趋势⑥"避免能力强但始终无法满足人的预期"；proactivity 已给诊断度量（proactivity.md:242）。
- 现状：用量页有 token 统计（README.zh.md:92-94）；诊断面板有错误；没有任务成功率/用户满意度/提案采纳率。
- 借鉴：在 proactivity 的度量上加三类：任务成功率（目标 `met` 数/目标总数）、用户干预率（被用户打断/纠正的回合占比）、记忆质量（被删/改的记忆占比）。只观察，不做 gate。
- 优先级：**观察**（等 P-02/T-12 有数据）。
- 验收：诊断面板能看到三项趋势；不引入遥测上传。

## 四、实施编排

### 4.1 编排原则

- **滚动批次**：每批是可独立验收的工作包，做完一批再开下一批；不排"大爆炸"式总计划。
- **拍板门**：触碰已定设计或边界（§五）的切片先过 §九 决策单；其余不阻塞。
- **不挡解耦主线**：批次 A/B 都在 `ds-bot/` 或 `app/` 壳内，与 B1 收尾、C0 并行；C 期间只做与自有工具面绑定的切片。
- **每片三个出口**：代码 + 测试（`npm test` / `--check` / lint）+ 一条可复现的验收命令或截图。验收没写清的切片不开工。
- **估时是量级**：天级按"一个有上下文的人"估；周级按"与主线并行"估。

## 五、与既有设计的冲突与裁决点

拍板时按顺序处理，前四条影响最大：

1. **proactivity 八条待拍板**（proactivity.md:270-279）——尤其是第 7 条"插件自起 tick 算不算 DSH 没有的能力"、第 8 条"目标 + live 是否越出'进度查询留给独立 app'"。这决定 P-02 能否现在做。
2. **"只提问不动手留给独立 app"**（bot-handoffs.md:114）——决定 P-05 `ask_bot` 是否可做。
3. **单机与端云**（vision.zh.md:36、proactivity.md:252）——T-08 的"用户自己的远端节点"是否算违反"数据留在用户自己电脑"？本文建议：**不算**，因为节点是用户自己的机器，数据不出用户控制范围；但要写进 vision 的取舍原则。
4. **记忆冻结 vs 画像/价值观注入**（context-and-memory.md:122-129）——T-01/T-11 若进提示词会破坏前缀缓存；本文建议 T-01 默认按需读取（`read_profile`），T-11 做短段（≤200 字）冻结注入。

## 七、不做什么

- **不做云端分身/厂商云**：数据留本机是取舍原则（vision.zh.md:36、proactivity.md:252）；端云只做用户自己的节点（T-08）。
- **不做 RSI 与提示词自动改写**：超出项目能力边界，且与"人类把关"的对齐观冲突（proactivity.md:76、247）。
- **不做世界模型/具身认知**：模型侧能力，DS Bot 只借鉴"操作前模拟"（T-06）。
- **不做多设备实时协作**：保持单写者；同步只做"只读跟随 + 显式主从"（T-09）。
- **不做无审批的 GUI 操作**：T-04 默认关闭、逐次审批。
- **不做微信个人号/短信/电话入口**：合规与成本问题（P-01 只做邮件/Telegram/Webhook）。
- **不做看板式任务对象**：沿用派活"活仍是消息"（bot-handoffs.md:114、proactivity.md:250）。
- **不做新记忆格式**：T-02 只在旁路建索引与可选元数据，不改 Markdown 本体。
